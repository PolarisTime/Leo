# Leo ERP dev 环境压测报告

- 执行时间：2026-09-29 21:45 - 22:32（Asia/Shanghai）
- 被测对象：`leo` 后端 dev 实例 `http://127.0.0.1:11211/api`（context-path `/api`）
- 数据库：PostgreSQL `leo`（**dev 库，非生产库**）；Redis `127.0.0.1:16379`
- 压测工具：k6 v0.54.0（与后端同机运行）
- 宿主规格：8 vCPU / 15 GiB，压测期间 swap 已占用约 10 GiB
- 测试账号：`admin_prod`（`permissions: ["*"]`）

## 一、执行摘要

| 结论 | 数据 |
|---|---|
| 读路径吞吐硬上限 | **约 830–850 req/s**，约 **50 VU 即饱和** |
| 达到上限后的行为 | 不再提升吞吐，**只线性增加延迟**；0 错误、0 5xx |
| 激进档是否报错 | **未报错**：800 VU 与 1500 VU 均 0 失败 |
| 最严重的真实缺陷 | **同账号并发登录 95% 失败**（92% 返回 409、3% 返回 500） |
| 写路径 | 50 VU 下 171 次「创建+删除」/s，0 失败 |
| 压测数据残留 | **0**（写测自清理，已复核） |

一句话结论：**读接口不会「压崩」，它会在约 50 并发时就到吞吐天花板，之后把压力全部转成延迟（1500 VU 时 p50 已达 1.96 s）；真正会报错的是登录接口，仅 20 个并发登录就会 95% 失败。**

## 二、测试方法

分五个阶段，全部通过 `leo/perf/run.sh` 驱动（脚本见同目录）：

1. **冒烟** `01-smoke.js`：1 VU 验证登录、10 个读接口、写链路（签发编码 → 创建客户 → 删除）。
2. **基线** `02-baseline.js`：1 VU 顺序轮询 60 s，测无竞争延迟。
3. **读混合爬坡** `03-read-mixed.js`：按权重随机访问各读接口，单调阶梯 51 → 150 → 300 VU，每档保持 45 s。
4. **写压测** `04-write-mixed.js`：50 VU / 2000 轮，每轮「签发客户编码 → 创建客户 → 删除客户」。
5. **激进档** `05-spike.js`：分别拉升至 800 VU 与 1500 VU 并保持。
6. **登录专项** `06-login.js`：同账号 20 VU × 10 轮，单独量化登录并发行为。

**关键方法说明**：读/写压测一律在 `setup()` 阶段**串行登录一次并共享 token**。原因是每个 VU 各自登录会触发下述登录缺陷，导致 VU 拿不到 token 而空转，把登录争用错误地混进读接口的测量结果——首轮未做此隔离时，读吞吐在约 40 VU 处被这个假象压到近乎为 0。

## 三、结果

### 3.1 冒烟

14/14 检查通过，读接口与写链路（`201` 创建 / `204` 删除）全通。

| `GET /v2.0/sales-orders?size=30` | 9.04 | 14.03 | 19.81 |
| `GET /v2.0/sales-orders?size=5` | 7.12 | 10.49 | 13.62 |

单请求延迟都很健康（全部 p95 < 15 ms），最重的全局搜索也只有 10 ms。

### 3.3 读混合爬坡（共 175,213 请求 / 0 失败 / 813.6 req/s）

按档位还原（数据来自逐请求 CSV）：

| 档位 | RPS | p50 (ms) | p95 (ms) | p99 (ms) |
|---|---:|---:|---:|---:|
| 保持 51 VU | 802.3 | 61.6 | 101.7 | 126.2 |
| 保持 150 VU | 815.4 | 177.9 | 309.4 | 399.7 |
| 保持 300 VU | 851.6 | 346.0 | 542.1 | 662.4 |

**并发从 51 涨到 300（5.9 倍），RPS 只从 802 涨到 852（+6%），而 p50 涨了 5.6 倍。** 吞吐在第一档就已到顶。

用 Little's law 交叉验证：300 VU / 852 req·s⁻¹ ≈ 352 ms，与实测 p50 346 ms 吻合，说明 300 个 VU 全程几乎都在排队等待，而非在计算。

逐接口在 300 VU 下高度一致，说明瓶颈是**共享资源**而非某个慢查询：

| 接口 | avg (ms) | p95 (ms) |
|---|---:|---:|
| `sales-orders?size=30` | 198 | 452 |
| `sales-orders?size=5` | 195 | 445 |
| `global-search` | 194 | 443 |
| `materials` | 190 | 440 |
| `customers` | 189 | 438 |
| `suppliers` | 187 | 434 |
| `account` | 184 | 436 |
| `company-settings` | 184 | 433 |
| `users` | 182 | 433 |
| `health`（不碰 DB） | 77 | 227 |

注意 `health` 既不查库也不走 JWT 过滤器，其 p95 仍退化到 227 ms——**这是「瓶颈在主机 CPU 层」的直接证据**，而不是数据库或某个接口的问题。

### 3.4 写压测（50 VU / 2000 轮 / 6001 请求 / 0 失败 / 514 req/s）

| 指标 | avg (ms) | p95 (ms) | p99 (ms) |
|---|---:|---:|---:|
| 创建客户 `POST /v2.0/customers` | 105.4 | 153.9 | 189.8 |

2000 次创建全部返回 `201`，2000 次删除全部返回 `204`，`write_customers_left_behind = 0`。

### 3.5 激进档：800 VU 与 1500 VU 均未报错

| 档位 | 请求数 | **失败** | RPS | avg | p95 | p99 |
|---|---:|---:|---:|---:|---:|---:|
| 800 VU | 144,139 | **0** | 846.2 | 597 ms | 1.14 s | 1.27 s |
| 1500 VU | 117,384 | **0** | 836.3 | 1.10 s | 2.13 s | 2.27 s |

1500 VU 保持档（保持 1500 VU 的 45 s 窗口）：RPS 834.0，p50 **1955 ms**，p95 2227 ms，p99 2349 ms。

**从 300 → 800 → 1500 VU，吞吐稳定在 813 / 846 / 836 req/s，一条几乎水平的线。** 到 1500 并发用户都没有出现错误或 5xx，也没有 dropped iterations。

### 3.6 登录专项：这是唯一真正会报错的地方

同账号 20 VU × 10 轮 = 200 次登录：

| 结果 | 次数 | 占比 |
|---|---:|---:|
| `200` 成功 | 10 | **5%** |
| `409` 乐观锁冲突（code 4090） | 184 | **92%** |
| `500` 系统异常（code 5000） | 6 | **3%** |

登录耗时也异常：avg 2.58 s、p95 3.85 s、max 3.94 s。

最小化复现（10 路并发 curl 同一账号）：**1 个 200、9 个 409**。

## 四、缺陷与根因

### 缺陷 1（严重）：同一账号并发登录 95% 失败

**根因**：`LoginService` 每次登录都执行 `user.setLastLoginDate(...)`，`sys_user` 实体带 `@Version` 乐观锁，且**冲突后不重试**。并发登录时多个事务对同一行做 read-modify-write，只有一个能提交：

```
ObjectOptimisticLockingFailureException: Batch update returned unexpected row count from update [0];
  actual row count: 0; expected: 1;
  statement executed: update sys_user set credential_version=?,...,last_login_date=?,...,version=? where id=? and version=?
```

**影响面**：不只是压测脚本。任何真实场景下同一账号的并发登录都会失败——用户开多个标签页/设备同时登录、多人共用账号、token 过期后的重登风暴。用户侧表现为「密码正确但登不进去」。

### 缺陷 2（严重）：20 个并发登录即打满数据库连接池，溢出请求变成 500

**根因**：登录事务持有一个 JDBC 连接去竞争同一行 `sys_user` 的行锁，被阻塞期间连接不释放。20 个并发登录正好占满 `maximum-pool-size: 20`，后续所有请求（包括读请求）都在 `connection-timeout: 3000` 后失败：

```
HikariPool-3 - Connection is not available, request timed out after 3000ms
  (total=20, active=20, idle=0, waiting=23)
```

登录压测窗口内共出现 **42 次**连接池超时。此时**没有任何读流量**，即登录路径单独就能耗尽整个连接池。

**次生问题**：连接池耗尽属于「服务暂时不可用」，语义上应是 `503 Service Unavailable` + `Retry-After`，但当前被 `GlobalExceptionHandler` 统一映射为 `5000 系统异常` / HTTP 500，会误导调用方与告警系统，客户端也无法做退避重试。

### 缺陷 3（中）：读路径缺少准入控制与背压

读路径不报错本身是好事（无崩溃、无泄漏），但系统对超载**完全没有拒绝能力**：无论 800 还是 1500 VU 都照单全收并排队，p50 涨到近 2 s。缺少限流/背压意味着上游一旦过载，延迟会无界增长直到客户端超时，影响面会扩散到所有用户。

### 观察：瓶颈在主机 CPU 层，不在数据库

- 归因：1500 VU 时 k6 侧 `http_req_blocked` avg 仅 **31 µs**，而 `http_req_waiting` avg **597 ms**，即耗时几乎全部花在等服务端响应，压测客户端不是瓶颈。
- 压测期间后端读路径 **0 WARN / 0 ERROR**，无 Hikari 超时、无 JPA 异常。
- 不查库的 `health` 接口 p95 同样退化到 227 ms。

## 五、优化建议

1. **修登录乐观锁冲突**（优先）
   - 把 `last_login_date` 的更新改为原子 `UPDATE sys_user SET last_login_date = ? WHERE id = ?`，绕开实体版本号；或
   - 对 `ObjectOptimisticLockingFailureException` 做有限次重试；或
   - 登录成功路径改为异步/批量刷写登录时间，不放在登录关键路径上。
2. **修连接池耗尽的错误语义**：把 `DataAccessResourceFailureException`（Hikari 超时）单独映射为 `503` + `Retry-After`，不要归入 `5000 系统异常`。
3. **给读路径加限流/背压**：按用户或全局维度限流，过载时快速返回 `429`，避免延迟无界增长。
4. **确认吞吐目标**：当前约 830–850 req/s 的上限包含了「k6 与后端抢同一台 8 核机器」的因素。若线上目标是更高吞吐，必须用独立压测机复测真实上限，再决定是否需要横向扩展或加缓存。
5. **关注 `sys_user` 行热点**：除登录外，任何高频更新同一 `sys_user` 行的逻辑都存在同类风险（如偏好设置、凭证版本）。

## 六、局限说明

1. **压测客户端与后端同机**：k6 与后端、PostgreSQL 共享 8 个核，压测期间宿主 load 峰值 39–41（8 核）。因此本报告给出的 ~850 req/s 是**同机竞争下的结果**，会低估独立压测机下的真实上限。
2. **沙箱无法观测后端进程**：后端跑在宿主上，沙箱内 `ps` 看不到，无法直接采集后端与 JVM 的 CPU/内存曲线，只能用宿主 `loadavg`/`free` 与 HTTP 指标间接推断。
3. **dev 数据量很小**：销售订单仅 87 条，读延迟不能反映生产数据量下的查询性能；本次结论主要反映框架吞吐与并发行为，而非 SQL 性能。
4. **登录专项只覆盖单账号**：本次环境仅有一个测试账号。多用户真实登录吞吐需通过 `LEO_PERF_LOGIN_POOL` 传入账号池后另测；同一账号的结论（5% 成功率）不直接等价于多账号场景。
