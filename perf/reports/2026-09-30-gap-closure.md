**最重要的两个发现不在原计划内**，但严重程度高于五项缺口本身：

## 二、第 1 项：并发正确性专项

方法：`08-concurrency.js`，三个场景各自并发 10 路。**并用 API 核对实际产生的业务数据**，不只依赖状态码。

| 场景 | 状态分布 | 实际业务结果 | 判定 |
|---|---|---|---|
| 同一角色权限并发替换 | 200×1,811 / **409×6,293（77.7%）** | 最终权限集恰为 `["roles:read"]`，count=1，**无重复无残缺** | 安全但噪声大 |
| 幂等键并发重放（同键） | 201×1 / 422×9 | **只创建 1 条**客户 | exactly-once 成立 |
| 同一客户编码并发创建 | 201×1 / 409×9 | **只创建 1 条**客户 | 唯一性正确 |

### 冲突机制与登录缺陷不同

`SysRolePermission` **没有 `@Version`**，因此 77.7% 的冲突**不是乐观锁**，而是
`deleteByRoleId` + `saveAll` 的「先删后插」在并发下撞唯一索引：该窗口内实测
**6,302 次 `DataIntegrityViolationException`**，与 6,293 个 409 响应基本一一对应
（两者互相印证）。

数据之所以仍然正确：失败事务会整体回滚（包括它已执行的删除），因此不会留下部分写入。
但这意味着客户端必须处理 77.7% 的冲突（6,293/8,104 = 77.65%），**服务端没有重试或排队**。

### 幂等重放的语义瑕疵

落败的 9 个同键请求返回 **422「客户编码未由系统签发或已失效」**，而不是重放首个请求的
响应，也不是明确的「处理中」冲突。exactly-once 的结果正确，但**调用方拿到的是一个
误导性的业务错误**，会以为自己提交的数据有问题。

### 测试过程中主动规避的一个风险

最初把并发写靶子定为内置 `SUPER_ADMIN` 角色。但全库**仅此一个内置角色**，
若并发写在其上产生部分写入，管理员将失去 `*` 通配权限，**连修复接口都会被 403 拦死**。
已改为临时创建专用角色作为靶子，用后删除（并复核 `SUPER_ADMIN` 权限仍为 `["*"]` 完好）。

## 三、第 2 项：服务端指标与缓存收益

### 补齐的测量盲区

新增 `collect-metrics.sh`，通过 `/actuator/prometheus` 采集压测期间的
Hikari 连接池（活跃/空闲/等待/**获取超时**）、JVM 堆与线程、Tomcat 忙碌线程、
进程/系统 CPU、Spring Cache 命中率、服务端请求直方图。

前置仅需环境变量 `LEO_MANAGEMENT_ENDPOINTS=health,prometheus,loggers`
（`micrometer-registry-prometheus` 依赖本就在 pom 中）。

> 口径限制：`cache_*` 只覆盖 Spring Cache region。权限缓存走
> `RedisJsonCacheSupport` 的裸 Redis 写入，**不产生 micrometer 缓存指标**，
> 因此权限缓存的收益体现在吞吐而非缓存命中率上。

### 缓存前后对比（300 VU 读爬坡，各一次干净运行）

| 指标 | 缓存前 | 缓存后 | 变化 |
|---|---:|---:|---:|
| 吞吐 | 813.58 req/s | **909.84 req/s** | **+11.8%** |
| avg | 185.55 ms | 166.14 ms | −10.5% |
| p95 | 437.98 ms | 372.57 ms | **−14.9%** |
| p99 | 564.85 ms | 451.60 ms | **−20.0%** |
| 失败 | 0 | 0 | — |

缓存后那次共 **195,620 请求、0 失败**。服务端窗口指标：连接池获取超时 **0**、
活跃峰值 20/20、**等待峰值 92**（连接池确有排队但未击穿）、JVM 堆 552 MB、
**system_cpu 峰值 100%**。

### 必须纠正此前的一个判断

上一份报告写过「缓存不会抬高 830 req/s 的天花板」。那是基于 CPU 归因的**推断**。
实测缓存使吞吐提升 11.8%：省掉每请求一次三表 join 后，单位请求的 CPU 成本下降，
同样的 CPU 就能处理更多请求。CPU 仍打满（100%），但**天花板确实被抬高了**。

## 五、第 4 项：Redis 降级与缓存雪崩

### 5.1 Redis 不可用 = 全站不可用（本报告最严重的发现）

隔离注入：只把 leo 后端指向不存在的 Redis 端口，**不触碰共享 Redis 实例**。

| 请求 | Redis 正常 | Redis 不可用 |
|---|---|---|
| `GET /v2.0/health` | 200 | **503 `DEGRADED`** ✅ 优雅 |
| `GET /v2.0/version` | 200 | 200 ✅（不依赖 Redis） |
| 已登录用户的**任何**接口 | 200 | **401「登录状态已失效，请重新登录」** ❌ |
| `POST /v2.0/auth/login` | 200 | **503「幂等服务暂不可用」** ❌ |

危害有三层：

1. **返回 401 而非 503**：客户端会误判为「我的登录过期了」，进而触发重新登录。
2. **重新登录也失败**：幂等过滤器依赖 Redis，登录直接 503。
3. **无法降级**：`CacheConfig` 的 `CacheErrorHandler` 优雅降级**只覆盖 Spring Cache**；
   认证链路用的是裸 `StringRedisTemplate`，`AuthenticatedUserCacheService.getActivePrincipal`
   对 Redis 调用**没有 try/catch**，异常穿透 `JwtAuthenticationFilter`
   （日志确认：`Connection refused` → `JwtAuthenticationFilter` 失败 → 401）。

**Redis 在本项目里不是可降级的缓存，而是硬依赖。** 另外
`scripts/backend/start-dev.sh` 含 Redis 预检，Redis 不可用时**直接拒绝启动**——
即故障期间连实例都无法拉起。

### 5.2 缓存冷启动雪崩（幅度有限）

用 Hibernate SQL 日志精确计数「权限查询」的实际执行次数：

| 场景 | 权限查询次数 |
|---|---:|
| 缓存热态，50 并发 | **0** |
| 轮换 epoch（权限缓存整体失效）后，50 并发 | **6** |

即：失效瞬间确实存在重复回源，但 50 个并发只产生 6 次查询，**幅度有限**——
因为请求到达天然错峰，先到的少数请求回源并回填后，其余即命中。

需要说明的局限：**没有单飞（single-flight）保护**，瞬时并发越高重复回源越多；
且本次用 curl 并发，进程启动天然错峰，**真实瞬时并发下会高于 6/50**。
另外只有**一个测试账号**，权限缓存只有 1 个 key，**多用户场景的雪崩无法模拟**。

## 六、第 5 项：Soak 长时稳定性

配置：`09-soak.js`，恒定 **40 VU**、**2 小时**、覆盖全部 21 个读接口、只读不产生业务数据。

选 40 VU 的依据：实测 **40 VU ≈ 1,010 req/s，高于 300 VU 的 909 req/s**，
说明 300 VU 已越过饱和点，40–50 VU 才是最优工作点。此前报告的
「830–850 天花板」其实是**过饱和后的数字**。

> **本节结论待补**：soak 仍在运行。泄漏判定使用 `collect-metrics.sh trend`
> （前后半段对比 + 最小二乘堆增长斜率），该检测器已用合成数据集验证
> （注入 +20 MB/h 精确检出 +20.00），并加了 **15 分钟最小观测窗口**保护——
> 短窗口下 JVM 预热会把正常服务误报成 +7000 MB/h 的假泄漏。

## 七、跨项发现：两个生产级风险

### 7.1 一次登录 409 可放大成全站雪崩

一次失败重跑中实测：**18,254 个请求里出现 3,615 次登录**、11,248 个 401、
4,359 个 500、409 个 409，**连接池获取超时 7,902 次**，失败率 **86.77%**。

链条：

```
setup 的一次登录被并发登录打成 409
  → 共享 token 为空
  → 每个 VU 每次迭代都重试登录
  → 登录需读改写同一行 sys_user（乐观锁，冲突后不重试）
  → 连接池被占满
  → 所有请求 500/401 → 雪崩自持
```

触发者是压测脚手架的登录竞争，但**放大器是系统本身**：登录路径的脆弱性
能把一个瞬态失败放大成全站故障。

### 7.2 同账号会话上限硬编码为 3，且静默踢人

```java
private static final int DEFAULT_MAX_REFRESH_TOKENS = 3;   // 硬编码，不可配置
```

同一账号第 4 次登录会吊销并拉黑最旧会话（`RevokeReason.CONCURRENT_LIMIT`），
其 access token 立即 401。客户端只看到「会话已失效」，**无法区分是自己登出还是被顶掉**。

影响面（不止压测）：
- **服务账号 / 监控账号 / 集成账号**与人工登录共用时互相顶掉；
- 用户在**第 4 台设备**登录会静默踢掉第一台；
- 上限**无法通过配置调整**，运维没有调节手段。

这一条也直接解释了本报告中的两次失败重跑（86.77% 与 92.52%）：压测用例、
指标采集器与辅助调用各自登录同一账号，会话被互相吊销。

### 7.3 既有登录缺陷（承前次报告）

`LoginService` 每次登录都写 `sys_user.last_login_date`，该实体带 `@Version`
乐观锁且冲突不重试。同账号 20 并发登录实测仅 **5% 成功**（92% 返回 409、3% 因
连接池耗尽返回 500）。20 个并发登录即可打满 `maximum-pool-size: 20`。

## 八、方法学缺陷与修正记录

本次自查并修掉了 4 个会污染结论的缺陷，一并记录以免误信早期数据：

| 缺陷 | 后果 | 修法 |
|---|---|---|
| 指标采集器每采样一次就登录 | 与用例 setup 抢会话，引发登录风暴 | 复用共享 token |
| `run.sh` / k6 setup 登录无重试 | 一次 409 静默退化成风暴 | 全流程**只登录一次** + 重试 |
| `ensureToken` 重登无退避 | 失败被逐迭代放大 | 失败后退避 2 秒 |
| 泄漏检测器无最小窗口 | 短窗口把 JVM 预热误报成泄漏 | 要求 ≥15 分钟才给判定 |

自查中发现的两个**我自己的错误**，也已修正：

- **测试构造错误**：`PageImpl` 在 `offset + pageSize > total` 时会把总数修正为
  `offset + content.size()`。我最初的断言用了「1 行数据却声称 total=7、pageSize=30」
  的不自洽组合而失败——这是测试问题，**原代码行为完全相同**。
- **误删已跟踪文件**：清理子代理新建目录时连带删除了同目录下已跟踪的
  `V2CashLedgerControllerPermissionTest.java`，已 `git checkout` 恢复并核对提交清单。

另需说明：**财务 `cashledger` 的重复聚合优化未纳入本次改动**。子代理在
修改这两个文件后失败退出且未做任何验证，我将其**存档后回退**
（`tmp/finance-wip.patch`、`tmp/finance-wip-tests/`），未提交任何未经验证的
财务 SQL 重写。`finance/overview` 的同类优化则是本人实现并完整验证后单独提交的。

## 九、局限

1. **压测客户端与服务端同机**，共享 8 核，CPU 峰值 100%。所有吞吐数字是
   **同机竞争下的结果**，会低估独立压测机下的真实上限；缓存 +11.8% 的对比
   也因此带噪（两次运行为各自独立的 JVM 实例）。
2. **dev 数据量极小**（销售订单 87 张），查询性能不代表生产；深翻页未测。
3. **仅一个测试账号**：权限缓存只有 1 个 key，多用户雪崩、多用户会话竞争无法模拟。
4. **沙箱无法观测宿主进程**：拿不到后端进程级 CPU/内存明细，只能用
   `/proc` 与 Prometheus 间接推断。
5. **附件路径未能压测（环境所限，非方法取舍）**：上传实测直接失败
   —— `S3 上传失败: HTTP 403 The Access Key Id you provided does not exist in our records`，
   即 `.env.local` 中的 COS/S3 凭据已失效。另外附件**没有删除接口**
   （只有 upload / access-url / content），即使能上传也无法清理，
   因此本环境下不对附件施加载荷。导入预览已覆盖（见第四节）。
6. **导出压测用的是单行单据**，生产多明细单据的开销未测。
7. 缓存前后对比为**各一次运行**，n=1，因果强度有限。

## 十、建议优先级

| 优先级 | 事项 | 依据 |
|---|---|---|
| **P0** | 让认证链路在 Redis 不可用时降级或返回 503 | 否则 Redis 抖动 = 全站登出且无法重登 |
| **P0** | 修登录乐观锁：原子 UPDATE 或有限重试 | 20 并发登录 95% 失败，且可放大为全站雪崩 |
| **P1** | 会话上限改为可配置，并给服务账号豁免机制 | 硬编码 3，静默踢人，自动化账号互相顶掉 |
| **P1** | 幂等重放失败者应重放首个响应而非 422 | 调用方会误判为自己提交的数据有问题 |
| **P2** | 导出接口增加并发上限或异步化 | 单请求 47–65 ms，是普通接口 8 倍 |
| **P2** | 权限并发写加服务端重试，减少 77.7% 的 409 | 客户端被迫处理大量冲突 |
| **P3** | 修复 dev 的 S3 凭据并补测附件上传/下载 | 附件路径当前完全未验证；另建议补删除接口以便清理 |
| **P3** | 用生产量级数据复测导出与导入预览 | dev 仅 87 张销售订单，重接口开销被严重低估 |
