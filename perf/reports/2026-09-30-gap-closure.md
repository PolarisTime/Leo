**除五项缺口外，本轮另外发现并修复了压测套件自身的 3 个缺陷**，它们都会制造「看起来像系统故障」的假数据：

1. **`ensureToken` 回归**：`07-heavy` / `08-concurrency` 的 setup 漏传 `expiresAt`，导致每个 VU 各自重登，触发服务端会话上限（3）的吊销级联 —— 实测 **99.3% 请求变 401**。
2. **指标采集器每次采样都登录**：`body="$(fetch_prometheus)"` 用命令替换调用，函数内的 `TOKEN=` 赋值只存在于子 shell，永远传不回父 shell。它每 ~6 秒登录一次，把正在被压测的会话顶掉。
3. **k6 没有阈值 ⇒ run.sh 假通过**：`07-heavy` 在 **98.05% 请求失败**时仍打印「07-heavy 通过」。

> 详情见第八节。这三条都是「工具在骗人」，不是系统的问题；它们也解释了为什么同一个脚本在不同时间给出了互相矛盾的结果。

**最重要的两个发现不在原计划内**，严重程度高于五项缺口本身：

1. **Redis 不可用会让所有已登录请求变成 500**（第 4 项，已实测确证）：不是优雅降级、也不是 503，
   而是未捕获的 `RedisConnectionFailureException` 直接穿透到客户端。即
   **Redis 抖动 = 全站 500 且无法重新登录**。
2. **登录脆弱性可放大成全站雪崩**：一次登录 409 会退化为登录风暴，实测打满连接池（7,902 次获取超时）、失败率 86.77%。同时发现**同账号会话上限硬编码为 3**，新登录会静默吊销最旧会话。

## 二、第 1 项：并发正确性专项

方法：`08-concurrency.js`，四个场景，各并发 10 路。**每个场景都用 SQL 核对实际产生的业务数据**，不只依赖状态码。
末次运行：`RUN_ID=20260930-052252`，9,538 请求、checks 100%、**非预期状态码计数 = 0**
（即没有任何 401/403/5xx 混入；409/422 是被测现象，不计为意外）。

| 场景 | 状态分布 | 冲突率 | 实际业务结果（SQL 核对） | 判定 |
|---|---|---:|---|---|
| A 同一角色权限并发替换 | 200×1,844 / **409×5,512** | 74.9% | 该角色权限**恰为 `["roles:read"]`，count=1**，无重复无残缺 | 安全但噪声大 |
| B 幂等键并发重放（同键） | 201×1 / 422×9 | — | 该场景**只创建 1 条**客户（`05:22:53` 唯一一行） | exactly-once 成立 |
| C 同一客户编码并发创建 | 1 成功 + 9 冲突 | — | 该编码**只创建 1 条**客户（`05:23:17` 唯一一行） | 唯一性正确 |
| D **同一单据并发整体替换** | 200×216 / **409×1,939** | **90.0%** | 单据 **version 3 → 220**，明细行数恒为 **1** | 无丢失更新 |

### 2.1 场景 D 是本轮新增的「同一单据」专项，也是最值得看的一条

A 场景写的是**单行记录**（角色权限），D 场景写的是**带明细行的单据**（销售订单，实体带 `@Version`）。
两者的失败模式不同：单据并发整体替换若发生部分写入，风险不只是版本冲突，而是**明细行重复或丢失**。

核对结论（`so_sales_order` + `so_sales_order_item`）：

- 2,155 次并发 PUT 中 216 次成功、1,939 次 409；
- 版本号 **220 = 运行前 3 + 预检 1 + 成功写入 216**，**精确相等**——每一次成功写入都真正落库，
  没有任何「返回 200 却被覆盖」的丢失更新；
- 冲突的 1,939 次没有静默覆盖别人，全部明确返回 409；
- 明细行数自始至终为 1，没有出现重复行或残缺；
- 单据状态仍为「草稿」，未被并发写意外推进流程。

代价：单据整体替换 **p95 = 104.07 ms**，约是角色权限单行写入的 2.6 倍（p95 39.75 ms），
且 90% 的请求被拒。**客户端若无重试策略，同一单据的并发编辑几乎必然失败一次以上。**

### 2.2 一个必须先纠正的测试设计错误：相同内容的并发 PUT 会被短路

第一版 D 场景让所有 VU 提交**完全相同**的 body。结果 596 次并发 PUT **全部返回 200、零冲突**，
看似「服务端完美串行化」。但 SQL 显示 **version 一次都没增长** ——
服务端把「内容无变化」的整单替换优化成了空操作。

也就是说：那 596 个 200 根本没写库，测试测的是「空写短路」，不是并发冲突。
把 remark 改成每请求唯一后，冲突率立刻变成 90.0%，version 也随成功次数精确增长。

**教训（已写进脚本注释）**：并发写专项必须让每个请求的内容**互不相同**，否则会把「无变化短路」
误读成「服务端串行化能力强」。这一点如果没有 SQL 侧核对版本号，是看不出来的。

### 2.3 冲突机制与登录缺陷不同

`SysRolePermission` **没有 `@Version`**，因此 A 场景的 74.9% 冲突**不是乐观锁**，而是
`deleteByRoleId` + `saveAll` 的「先删后插」在并发下撞唯一索引（前期实测对应 6,302 次
`DataIntegrityViolationException`，与 409 数量基本一一对应）。
D 场景的冲突则来自销售订单实体的 `@Version` 乐观锁：`LoginService` 同类问题（冲突后不重试）。

数据之所以仍然正确：失败事务会整体回滚。但**服务端没有重试或排队**，
A/D 两个场景分别把 74.9% 与 90.0% 的冲突处理责任推给了客户端。

### 2.4 幂等重放的行为是正确的（本条初稿误判，已更正）

初稿曾写「落败的 9 个请求返回 422『编码已失效』，属语义瑕疵」。核对代码与日志后确认
这是**误判**：那 10 条 `code=4000` 日志来自更早一次跑的**测试设计缺陷**——该场景复用了已被消耗的编码。

修复场景设计后的准确行为：落败的 9 个同键请求由幂等过滤器返回
**422 + code=4220**「请勿重复提交，请等待当前请求处理完成」，即正确识别出
「同一幂等键的并发请求正在处理中」。该响应经 `ApiErrorResponseWriter` 直接写出，
**绕过全局异常处理器因而没有日志**——这正是最初被误导的原因。

结论：exactly-once 成立，并发冲突也给出了明确反馈，**行为正确**。
唯一可议之处是状态码选择：并发重复提交更惯例用 **409 Conflict**，
当前用 422，属 API 约定问题而非缺陷。

### 2.5 测试过程中主动规避的两个风险

- **不拿内置角色做靶子**：全库**仅有 `SUPER_ADMIN` 一个内置角色**，若并发写在其上产生部分写入，
  管理员将失去 `*` 通配权限，连修复接口都会被 403 拦死。已改为临时创建专用角色作为靶子。
- **单据靶子只挑「可写的草稿」**：PUT 对**已软删**单据返回 404（dev 库 10 张草稿里有 9 张是
  E2E 软删残留），若不做预检，场景会把「单据不可写」误读成「并发冲突」。
  脚本现在先按状态筛出草稿单、再**预检一次 PUT 必须 200**，否则直接中止。
  实测可写草稿单**全库仅 1 张**（`358235006335713280`），测试后已把 remark 还原为原值
  `E2E-B-1789448269548-SO-2`（version 因测试推进到 221，属预期副作用，已在 README 说明）。

## 五、第 4 项：Redis 降级与缓存雪崩

### 5.1 Redis 不可用：登录 503、health 503、已登录请求 500（初稿结论已撤回）

隔离注入：只在 **11212** 另起一个「故障实例」，把它的 Redis 端口指向不存在的端口；
**11211 上的正常实例与共享 Redis 实例都不被触碰**。

| 请求 | Redis 正常 | Redis 不可用 | 证据强度 |
|---|---|---|---|
| `GET /v2.0/health` | 200 | **503 `DEGRADED`** | ✅ 确证 |
| `GET /v2.0/version` | 200 | 200（不依赖 Redis） | ✅ 确证 |
| `POST /v2.0/auth/login` | 200 | **503「幂等服务暂不可用」** | ✅ 确证 |
| `GET /v2.0/account`（有效 token） | 200 | **500 `RedisConnectionFailureException`** | ✅ 确证 |
| `GET /v2.0/sales-orders`（有效 token） | 200 | **500 `RedisConnectionFailureException`** | ✅ 确证 |
| `GET /v2.0/account`（坏签名 token） | 401 | 401（判别探针） | ✅ 确证 |

故障实例日志：`RedisConnectionFailureException` **4 次**，`ExpiredJwtException` / `JwtException` **0 次**。

**因果链是被三重对照锁住的，不是靠时间巧合推断的**：

1. **双实例并行**：探测期间不需任何重启等待。基线 token 剩余有效期 **600 s**（阈值 120 s），
   两次 `assert_token_valid` 都记录「剩余 600s」——从一开始就排除了「token 过期」这一混淆项；
2. **同 token 活性对照**：探测故障实例**前 1 秒**，用**同一个** token 打正常实例，
   `/account` 与 `/sales-orders` 都是 **200**；紧接着用同一 token 打故障实例得到 500。
   同一个 token、同一时刻、只有一个变量不同（Redis），因果明确；
3. **坏签名判别探针**：故障实例上把签名段篡改后请求 → **401**（而不是 500），
   说明 500 不是「密钥不一致/签名失败」造成的，而是**签名校验通过之后**、认证链路访问 Redis 时抛出的。

> **本节初稿的两处断言都已被推翻，记录如下：**
> 初稿曾写「Redis 不可用时已登录用户全部收到 **401**」。复核发现：
> (a) 那些 401 的真实原因是 `ExpiredJwtException`（初版脚本「取 token → 停后端 → 换端口重启 → 探测」
> 的流程耗掉约 11 分钟，超过 600 s 有效期）；(b) 真正的表现根本不是 401，而是 **500**。
> 初版脚本的守卫已重写为双实例 + 活性对照 + 判别探针（`redis-degradation.sh`），
> 并有 `perf/test/token-guard-selftest.sh` 对守卫做双向验证（有效 token 通过、过期/阈值内/非 JWT 被拦）。

**后果（现在可以确证了）**：

1. **Redis 是本项目的硬依赖，且没有降级路径**：`CacheConfig` 的 `CacheErrorHandler` 优雅降级
   **只覆盖 Spring Cache**；认证链路用的是裸 `StringRedisTemplate`，
   `AuthenticatedUserCacheService.getActivePrincipal` 对 Redis 调用**没有 try/catch**，
   且异常不在 `JwtAuthenticationFilter` 捕获的 `JwtException | IllegalArgumentException` 之内，
   于是直接变成 **500**。
2. **故障期间无法重新登录**：幂等过滤器同样依赖 Redis，登录返回 503。
   即 Redis 抖动期间，**在线用户全部 500、且没人能重新登录**。
3. **对监控不友好**：基础设施不可用被报成 `500 Internal Server Error`（5000），
   与代码缺陷同码；正确的语义应是 **503 + Degraded**，否则告警无法区分「依赖挂了」与「代码炸了」。
4. `scripts/backend/start-dev.sh` 含 Redis 预检，Redis 不可用时**直接拒绝启动**——
   故障期间连实例都无法拉起。

### 5.2 缓存冷启动雪崩（幅度有限）

用 Hibernate SQL 日志精确计数「权限查询」的实际执行次数：

| 场景 | 权限查询次数 |
|---|---:|
| 缓存热态，50 并发 | **0** |
| 轮换 epoch（权限缓存整体失效）后，50 并发 | **6** |

即：失效瞬间确实存在重复回源，但 50 个并发只产生 6 次查询，**幅度有限**——
因为请求到达天然错峰，先到的少数请求回源并回填后，其余即命中。

需要说明的局限：**没有单飞（single-flight）保护**，瞬时并发越高重复回源越多；
且本次用 curl 并发，进程启动天然错峰，**真实瞬时并发下会高于 6/50**。
另外只有**一个测试账号**，权限缓存只有 1 个 key，**多用户场景的雪崩无法模拟**。

## 六、第 5 项：Soak 长时稳定性

配置：`09-soak.js`，恒定 **40 VU**、**2 小时**（因为 access token 600 s 不可配置，按 8 分钟分段运行、

### 泄漏判定：无泄漏（并且修掉了检测器的一次误报）

服务端堆是典型的**锯齿波**：2 小时里峰谷幅度 **418.9 MB**、**86 次 GC**、合计回收 **15,027 MB**。

检测器最初只看**均值**的最小二乘斜率，于是报出 **+18.92 MB/h「疑似内存泄漏」**。
但同一份稳态负载在 71.8 分钟窗口算出的是 **−65.13 MB/h**——正负相反，
说明该指标被 GC 相位主导，不可用。

改为「分桶最小值（≈GC 后存活水位）的斜率 + 显著性检验」后：

```
锯齿诊断: 峰谷幅度 418.9 MB，GC 回收(单次 >10MB) 86 次，共回收 15027 MB
堆内存存活水位斜率(GC 后最小值, 12 桶): +6.98 ± 10.83 MB/小时（t=0.64）
  首桶水位 274.7 MB → 末桶水位 259.3 MB
堆内存增长判定: +6.98 MB/小时，但 t=0.64 < 2（漂移在噪声范围内）  ✅ 未见泄漏迹象
```

即：**斜率远小于自身噪声（t=0.64）、首末桶水位没有上升（末桶反而更低）**，判为无泄漏。
另外窗口末值（372.7 MB）低于窗口首值（422.6 MB），也与「单调泄漏」相矛盾。

检测器已用合成数据双向验证（`perf/test/leak-detector-selftest.sh`，7 项断言全部通过）：
注入 +60 MB/h → 报泄漏（t=56.2）；注入 +20 MB/h → 报泄漏（t=14.7）；
水位恒定 → 不报；**水位恒定但带 ±25 / ±35 MB 抖动（与真实数据同量级）→ 不报**（旧逻辑会误报）；
10 分钟窗口 → 拒绝判定。

## 七、跨项发现：两个生产级风险

### 7.1 一次登录 409 可放大成全站雪崩

一次失败重跑中实测：**18,254 个请求里出现 3,615 次登录**、11,248 个 401、
4,359 个 500、409 个 409，**连接池获取超时 7,902 次**，失败率 **86.77%**。

链条：

```
setup 的一次登录被并发登录打成 409
  → 共享 token 为空
  → 每个 VU 每次迭代都重试登录
  → 登录需读改写同一行 sys_user（乐观锁，冲突后不重试）
  → 连接池被占满
  → 所有请求 500/401 → 雪崩自持
```

触发者是压测脚手架的登录竞争，但**放大器是系统本身**：登录路径的脆弱性
能把一个瞬态失败放大成全站故障。

### 7.2 同账号会话上限硬编码为 3，且静默踢人

```java
private static final int DEFAULT_MAX_REFRESH_TOKENS = 3;   // 硬编码，不可配置
```

同一账号第 4 次登录会吊销并拉黑最旧会话（`RevokeReason.CONCURRENT_LIMIT`），
其 access token 立即失效。客户端只看到「会话已失效」，**无法区分是自己登出还是被顶掉**。

影响面（不止压测）：
- **服务账号 / 监控账号 / 集成账号**与人工登录共用时互相顶掉；
- 用户在**第 4 台设备**登录会静默踢掉第一台；
- 上限**无法通过配置调整**，运维没有调节手段。

这一条也直接解释了本报告中的多次失败重跑：压测用例、指标采集器与辅助调用各自登录同一账号，
会话被互相吊销。现在套件已强制共用同一个 token，并且采集器会对「登录次数 > 1」显式告警。

### 7.3 既有登录缺陷（承前次报告）

`LoginService` 每次登录都写 `sys_user.last_login_date`，该实体带 `@Version`
乐观锁且冲突不重试。同账号 20 并发登录实测仅 **5% 成功**（92% 返回 409、3% 因
连接池耗尽返回 500）。20 个并发登录即可打满 `maximum-pool-size: 20`。

## 八、方法学缺陷与修正记录

### 8.1 本轮自查并修掉的、会污染结论的缺陷

| 缺陷 | 后果 | 修法 |
|---|---|---|
| **`ensureToken` 回归**：`07-heavy`/`08-concurrency` 的 setup 漏传 `expiresAt` | `now < (undefined\|\|0) - 60s` 恒为假 → 每个 VU 各自重登 → 触发会话上限级联 → **99.3% 请求 401**（346,686 掉 339,955），业务日志几无异常 | setup 改为整体展开 `base`；`ensureToken` 增加「`expiresAt` 缺失时回退解析 JWT exp」双保险 |
| **采集器每次采样都登录**：`body="$(fetch_prometheus)"` 命令替换导致 `TOKEN=` 赋值丢失在子 shell | 每 ~6 秒登录一次，把正在被压测的会话顶掉 → 一次 07-heavy 的 **99.3% 请求变 401** | 改为「写临时文件 + 登录计数」，并对 `登录次数 > 1` 显式告警 |
| **k6 没有阈值 ⇒ run.sh 假通过** | 98.05% 失败的运行照样打印「07-heavy 通过」 | 07-heavy 增加按 `kind` 的失败率阈值与 checks 阈值；08-concurrency 增加 `race_unexpected_status`（只允许 200/201/409/422）；run.sh 增加失败率兜底阈值并以非零退出码结束 |
| 相同内容的并发 PUT 被服务端短路 | 596 次并发 PUT 全部 200 却零写入，会被误读成「服务端串行化很好」 | 并发写必须内容互不相同；并用 SQL 核对 version 增量 |
| 附件上传不可用 | 无法压测附件路径 | 记录为环境限制（见第九节），不施加载荷 |

**验证证据（不是「应该修好了」）**：

- `perf/test/collector-login-selftest.sh`：本地桩服务计数登录次数 —— 未提供 token 时整个采集过程
  **恰好 1 次**登录、提供共享 token 时 **0 次**、取指标周期性失败时重登并打印告警（7 项断言全过）；
- 修复后重跑 07-heavy：`auth_refresh_token` 表在整批（10 分钟）内**只新增 1 条会话**，
  k6 内部登录次数 **0**，67,333 请求 **0 失败**；
- 负例对照：故意破坏签名 → k6 退出码 107；故障实例未起时 30 VU 部分失败 → 退出码 99（阈值拦截）；
- 06-concurrency 复跑：`race_unexpected_status = 0`，确认历史 77.6% 的数字**没有**被 401 污染。

### 8.2 早前已修正的缺陷（保留记录）

## 九、局限

1. **压测客户端与服务端同机**，共享 8 核，CPU 峰值 100%。所有吞吐数字是
   **同机竞争下的结果**，会低估独立压测机下的真实上限；缓存 +11.8% 的对比
   也因此带噪（两次运行为各自独立的 JVM 实例）。
2. **dev 数据量极小**（销售订单 87 张、明细 1 行），查询与导出性能不代表生产；深翻页未测。
   导出在并发下从 4.5 ms 放大到 100 ms 是**同机 CPU 争用**的结果，生产量级（多明细行）会更高。
3. **仅一个测试账号**：权限缓存只有 1 个 key，多用户雪崩、多用户会话竞争无法模拟。
4. **沙箱无法观测宿主进程**：拿不到后端进程级 CPU/内存明细，只能用 `/proc` 与 Prometheus 间接推断。
5. **附件只覆盖了 local 存储口径**：S3/COS 路径仍未验证——`.env.local` 里的凭据已失效
   （`S3 上传失败: HTTP 403 The Access Key Id you provided does not exist in our records`）。
   第四节的上传/下载数字来自 `leo.attachment.storage.type=local`，
   **不含 S3 客户端、签名 URL 与对象存储网络往返**。另外附件**没有删除接口**
   （只有 upload / access-url / content），压测数据只能靠 `cleanup-perf-data.sh --attachments` 走 SQL 清理。
6. **同一单据并发写只有 1 张可写草稿单**（其余草稿为 E2E 软删残留，PUT 返回 404），
   因此 D 场景只能针对单张单据、且会推进其 `version`（测试后 remark 已还原）。
   新建一张可写单据在 dev 库不可行：**采购来源明细已全部被占用**（`source-candidates` 返回 0 条），
   而业务规则要求「每行必须且只能选择一个采购来源明细」。
7. 缓存前后对比为**各一次运行**，n=1，因果强度有限。
