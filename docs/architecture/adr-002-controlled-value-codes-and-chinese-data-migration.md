# ADR-002：受控业务值使用稳定编码与中文展示分离

## 状态

已采纳，2026-09-01；根据严格评审意见修订；数据库与接口迁移待实施。

## 背景

对 Leo 和 Aries 的静态检查确认，当前系统把中文同时用于两种不同性质的数据：

1. **受控业务值**：状态、类型、方向、结算方式、单位、调整原因、菜单/操作标识等。这些值会参与状态机、分支判断、统计、筛选、事件和权限判断。
2. **用户业务文本**：客户、供应商、项目和商品名称，联系人、地址、备注、合同条款、打印模板正文及历史快照。这些内容本身就是用户输入，不能被编码替代。

当前两种数据混用中文值和英文编码。例如 `StatusConstants` 中存在 `正常`、`禁用`、`草稿`，而付款用途已经使用 `STATEMENT_SETTLEMENT`、`PURCHASE_PREPAYMENT`，打印模板状态也使用 `ACTIVE`、`DISABLED`。中文文案一旦修改、翻译或出现同义词，直接比较中文的代码、SQL、缓存和事件就会产生漂移。

本决策覆盖 Leo 数据库、Leo API/事件、Aries API 适配和前端显示；不要求把所有中文业务内容翻译成英文，也不改变已落库的历史名称和正文。

## 现状证据

以下位置代表受控值已经作为真实数据使用，迁移时必须按列核对，不能进行全库字符串替换：

| 类别 | 当前示例 | 证据 |
| --- | --- | --- |
| 单据状态 | `草稿`、`已审核`、`完成采购`、`完成销售` | `src/main/java/com/leo/erp/common/support/StatusConstants.java`、各单据实体/服务 |

| 往来方类型/方向 | `客户`、`供应商`、`物流商`、`应收`、`应付` | 财务服务和基础种子数据 |
| 计量方式/单位 | `过磅`、`理算`、`件`、`吨`、`次` | 交易、物流和物料模块 |
| 调整原因 | `增加余额`、`减少余额`、`坏账`、`抹零` | 财务台账调整服务 |

| 已有编码模式 | `STATEMENT_SETTLEMENT`、`PURCHASE_PREPAYMENT`、`ACTIVE`、`DISABLED` | `PaymentPurposes`、`PrintTemplateApplyService` |

## 业内做法与方案比较

业内普遍采用“稳定技术编码 + 可本地化展示文本”的两层模型：机器只依赖编码，界面和报表根据语言、租户和上下文解析标签。编码通常使用大写 ASCII 和下划线，数据库使用 `VARCHAR`，由后端常量、校验器或字典表约束；不推荐把业务流程绑定到数据库原生 `ENUM`，因为新增值和跨版本部署成本较高。

| 方案 | 优点 | 风险/代价 | 结论 |
| --- | --- | --- | --- |
| 数据库存中文并在代码中比较 | 改动少 | 文案变更即语义变更，难以国际化，事件/缓存容易出现同义值 | 不采用 |
| 全部字段改成英文编码 | 机器值稳定，便于统计和集成 | 会破坏用户名称、备注、合同和模板等自然语言数据 | 不采用 |
| 受控值编码，用户文本保留原文 | 兼顾稳定性、国际化和审计；可逐步扩展字典 | 需要一次数据迁移和边界治理 | **采用** |
| 数据库原生 `ENUM` | 数据库层约束强 | 迁移和多服务版本协商复杂，难以支持租户/语言/废弃生命周期 | 不采用 |

## 决策

### 1. 受控值的存储规范

- 受控值在数据库、API 请求/响应、消息、缓存 key 和报表维度中使用稳定 ASCII `code`。
- 编码必须全部由大写 ASCII 字母、数字和下划线组成，且以 ASCII 字母开头，正则为 `^[A-Z][A-Z0-9_]*$`；禁止小写字母、空格、连字符和中文。系统级编码统一以 `VARCHAR(64)` 为最大存储上限，租户自定义编码默认不超过 `VARCHAR(32)`；迁移盘点必须为每个受控列核对实际最大长度，列宽不足时先扩容再迁移。编码一经发布不可重命名、不可复用；不再使用时标记废弃。
- 固定流程状态由后端常量/状态机定义并校验迁移边；可配置选项由字典表定义。两者都不能用显示文案作为分支条件。
- 数据库优先使用 `VARCHAR` 加非空、长度和必要的格式约束。固定状态可增加 `CHECK` 或服务端白名单；不把数据库原生 `ENUM` 作为跨模块契约。

### 2. 展示文本与 API 契约

- 资源的受控字段传输编码，例如 `status: "DRAFT"`；需要直接展示时同时返回 `statusLabel`，或由选项接口返回 `{ code, label, locale, sortOrder, enabled }`。
- Aries 页面、筛选器、表格排序和 Zod schema 只依赖 `code`，显示文案统一来自 i18n/字典元数据。禁止在业务逻辑中写 `status === "草稿"`。
- 旧客户端不能静默接收新值。若现有 API 版本已经被使用，使用并行版本/适配层：旧版本在边界把 code 转为历史中文，新版本只返回 code（可附 label）。兼容窗口必须有截止日期和调用方清单。
- 旧版 API 在兼容窗口内的写入请求同时接受历史中文和新 code；边界适配层按“版本 + 资源 + 字段语义”转换为 code，核心服务层只接收 code。无法映射、映射歧义或格式非法时返回 `422`，并记录 `legacyValue`、调用方版本、资源字段和 traceId；窗口结束后旧中文输入必须拒绝。
- OpenAPI、SDK、事件 schema、导入导出说明和前端类型必须在同一变更中更新。新增接口遵守现有 `/api/v2` 资源规范；破坏既有契约时按版本策略发布，不能借“数据库一次性切换”绕过 API 兼容要求。

### 3. 字典模型与生命周期

固定状态不强行建通用字典；确有租户可配置需求时采用三层概念：

- 字典类型：`dictTypeCode`、所属模块、作用域（系统/租户）、是否允许自定义。
- 字典项：`dictTypeCode`、`itemCode`、启用/停用/废弃状态、排序、扩展元数据。`(scope, dictTypeCode, itemCode)` 唯一。
- 标签：`dictTypeCode`、`itemCode`、`locale`、`label`。同一语言唯一，按 `locale -> 租户默认语言 -> 系统默认语言` 回退。

业务表保存 `itemCode`，不保存可变 label。只有审计、打印或不可变历史快照明确需要时，才额外保存当时的 `labelSnapshot`；快照不能反过来参与业务判断。

### 4. 数据库迁移方式

这是一次性业务切换，但必须作为破坏性版本发布处理。默认采用“停写后一次切换”；若业务不能接受停写，必须先发布支持双写/读兼容的过渡版本，不能让旧版本直接面对新约束。

1. **盘点与冻结**：冻结受控字段清单、映射表、未知值处置和 API 兼容窗口；停止新增中文种子和代码比较。
2. **预检与备份**：在生产副本上统计每个表/列的 distinct 值、空值、未知值和歧义值；完成可恢复备份和恢复演练，记录行数、索引及校验和。
3. **维护窗口停写**：停止 Leo 实例、定时任务、消息写入者和后台脚本，确认没有旧版本继续写入。
4. **Flyway 迁移**：在 `V1__baseline.sql` 之后新增递增脚本。未知或歧义值必须抛错并回滚，禁止 `COALESCE` 成猜测编码。小表只有在单表行数不超过 `100000` 且生产同构演练证明排他锁预计不超过 `30` 秒时，才允许原地更新；超过任一门槛或锁风险未知，必须使用影子列：
   - 新增可空的 `*_code` 影子列，不删除旧列；
   - 按映射清单回填并校验行数、非空、格式、唯一性和未知值；大表按批次回填并记录进度，停写窗口内完成最终追平；
   - 应用切换为读取/写入 code，旧列在回滚窗口内只读保留；
   - 验证完成后再设置 `NOT NULL`、默认值、`CHECK`、索引和字典约束；
   - 回滚窗口结束后通过后续 Flyway 删除旧列或将其标记为废弃，不能在同一脚本中不可逆删除。
   原地更新也必须遵循“先完成值转换和完整性验证，再设置约束、默认值、索引和非空”的顺序。
5. **应用切换**：按下方发布时序部署 Leo 和 Aries；事件消费者、报表任务和导入作业必须与新编码版本同时就绪。
6. **缓存与客户端清理**：刷新 Redis、localStorage、IndexedDB、Service Worker 和 CDN 缓存，避免旧筛选条件或旧字典继续回写中文。
7. **验证后放流**：执行核心单据、状态迁移、导入导出、报表、打印、权限和消息消费冒烟；确认“中文受控值写入计数”为零后解除停写。

一次发布窗口可以执行多条职责清晰的 Flyway，但不得直接在环境中手工执行持久化 SQL，也不得修改已经执行过的基线或历史脚本。大表更新需单独评估锁等待、事务大小、表膨胀、索引重建和 vacuum；必要时先在兼容窗口完成影子列回填，再在停写窗口切换约束。

默认停写发布时序如下：

```text
停止旧 Leo 实例、定时任务、消息生产者
        -> 备份/恢复点确认与迁移预检
        -> 执行 Flyway 数据转换和约束切换
        -> 部署事件兼容适配器/新消费者
        -> 部署并启动新 Leo（新生产者只发布 code）
        -> 部署 Aries，清理缓存和客户端旧状态
        -> 核心业务、契约、事件、报表、打印冒烟
        -> 确认中文受控值写入计数为零
        -> 恢复流量
```

如果无法完全停写，必须先部署双写兼容版本：旧列和 code 列在同一事务写入，读路径优先 code 并能回退旧列；影子列回填和一致性监控完成后，才能执行最终切换。禁止在旧版本仍运行时先施加只接受 code 的数据库约束。

### 5. 兼容与回滚

- 数据库内部切换后只接受 code。导入层可在有限窗口接受旧中文并转换，同时记录 `legacyValue`、映射结果和操作者；窗口结束后拒绝旧值并返回明确错误。
- 事件 envelope 必须增加 `schemaVersion`。兼容窗口内，边界适配器按版本将旧中文 payload 转为内部 code；新生产者只发布新版本和 code，业务消费者只依赖 code。无法升级的旧消费者必须由适配器或独立兼容订阅承接，不能假设它能直接比较新 code；兼容期结束后删除旧分支和监控告警。
- 回滚分为两级：一级是反向迁移，适用于映射双射、没有新增自定义值且事件/审计能够接受反向表示的场景，可保留迁移后的新数据；二级是备份恢复，适用于反向迁移不可行的场景，必须再次停止写入、明确恢复点后新增数据的丢失范围，并由业务负责人批准。回滚代码不能自动回滚数据，也不能把备份恢复描述成无损操作。
- 迁移失败时保持数据库原值和应用旧版本可运行；不得留下“部分表已编码、部分表仍中文”的混合写状态。

## 验证与质量门禁

迁移实施前后至少执行以下检查：

- SQL 预检：每个受控列的未知值数为 0，映射后 code 唯一、非空且满足格式约束。
- 后端测试：状态机、权限、统计、并发更新、审计事件、缓存失效和旧值拒绝；金额、重量和雪花 ID 契约不受影响。
- 前端测试：Zod schema、筛选/排序、状态标签、表单回填、离线草稿清理和语言切换；不得把 code 当作用户可编辑名称。
- 契约测试：OpenAPI、请求/响应 DTO、事件 schema、导入导出样例和错误码同步；旧版本适配层覆盖成功与失败路径。
- 静态门禁：扫描 Java/TypeScript/SQL/seed，禁止生产受控字段与中文字面量比较或新增中文种子；测试文件（如 `*.test.ts`、`*.spec.ts`、`*Test.java`）可包含中文兼容夹具，但必须标明 legacy/compatibility 用途。生产代码中的中文只能属于 label、快照、模板正文等已声明类别，并通过注释、命名约定或注册表 allowlist 识别。
- 运行观测：上线期间记录旧值转换数、未知值拒绝数、字典未命中数和事件消费失败数，按租户和模块可追踪。

## 后续扩展约束

1. **编码治理**：在 Leo 仓库新增 `config/business-codes.yml` 作为集中注册表，至少记录 `domain`、`dictTypeCode`、`code`、作用域、owner、首次版本、状态、废弃时间、替代编码和默认 label。CI 新增注册表校验脚本，扫描 Java/TypeScript/SQL/seed 中的受控 code，与注册表比对并阻止未注册、重命名、复用和跨字典冲突；迁移脚本中的新 code 必须先登记，不能只在 SQL 中硬编码。
2. **国际化**：标签按 locale 管理，默认语言回退可观测；业务数据中的中文名称不通过拼音或机器翻译替换。字典标签可提供按 label 的模糊搜索，但业务查询不依赖 label 精确匹配；排序优先使用 `sortOrder`，需要按语言排序时使用明确的 locale/collation 规则，另行记录性能和一致性决策。
3. **多租户**：系统级编码与租户自定义编码分离，查询必须带作用域；租户不能覆盖固定状态的语义。
4. **报表与数仓**：事实表按 code 统计，维表提供多语言 label；历史报表按当时 code 重放，不能因当前文案修改而改变历史含义。
5. **审计与不可变事件**：操作日志同时保存 `actionCode` 和 `actionLabelSnapshot`；事件 payload 只把 code 作为机器字段，必要的展示文本作为快照，不依赖实时字典才能重放。
6. **扩展状态机**：出现跨事务、人工审批、定时升级或长流程时，重新评估持久化工作流；编码迁移本身不引入 BPMN 或第三方状态机。
7. **防回退**：新增模块必须从编码开始设计，禁止复制中文状态常量、中文 URL 查询值、中文 Redis key 或中文 OpenAPI 枚举示例。

## 实施前置条件

开始写迁移脚本前必须由产品、后端和前端共同确认：

- 最终的“表 + 列 + 语义”盘点和一对一映射清单；
- 固定状态与可配置字典的边界、编码 owner 及生命周期；
- API 兼容窗口、旧客户端清单、事件版本和下线日期；
- 历史报表、审计和打印是否需要 label 快照，并形成具体的表/字段清单、保留期限和变更责任人；只有清单内的不可变业务事实才允许写入 `labelSnapshot`；
- 数据量、锁等待预算、维护窗口、备份恢复验证和反向迁移方案。

在上述条件未签字确认前，不执行生产数据更新，也不修改现有 Flyway 基线。
