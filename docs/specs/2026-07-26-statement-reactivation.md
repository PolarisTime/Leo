# 背景

V96（simplify_finance_workbench）将客户/物流对账单定位为“历史资料”，收付款流程改为直接按往来单位与结算主体确认；前端对账页面以 `hiddenInMenu` 隐藏。解耦计划（2026-07-24）明确“对账与财务当前未实际使用，只隔离边界”，并约定“实际启用应另行业务口径评审”。

2026-07-26 业务方确认重新启用对账模块，本文档即该评审的结论落档。

# 决策

1. **启用范围**：客户对账单、物流对账单两个模块恢复为在用流程；前端“对账”菜单组显现。
2. **结算口径**：对账单与收付款保持**可选关联**（维持 V96 现状）——收付款可直接确认，也可关联已确认/已审核对账单核销；不恢复结算强前置。
3. **供应商对账**：不启用。代码残留（常量、锁 SQL、恒 null 字段）已清理；`st_supplier_statement` 数据表及主数据引用检查保留（可能含迁移前历史数据），确认表为空后可另行出 DROP 迁移。
4. **汇总能力**：客户对账新增 `GET /customer-statements/summary`（口径对齐物流侧 `/freight-statements/summary`：单据数、销售金额、收款金额、期末余额）。
5. **打印**：`print-runtime.json` 与前端打印目标清单已含两个对账模块，打印模板按项目惯例人工制作并导入，不新增代码。

# 状态流转（不变更）

- 客户对账单：待确认 ↔ 已确认；已确认后允许收款核销；反确认/删除前守卫内锁自身行并校验无已审核核销。
- 物流对账单：草稿 ↔ 已审核；已审核后允许付款核销；反审核/删除守卫同上。

# 相关变更

- 前端：`page-registry-finance.ts` 菜单显现；旧的“按往来单位+期间”生成通道（`ModuleStatementGenerator` 等）已删除，生成统一走编辑器 + 来源导入。
- 后端：`CustomerStatementSummaryQueryRepository` 等新增；供应商对账残留清理见上。
- 数据库：V111 更新两张对账表注释。

# 重评条件

- 业务要求对账单成为收付款强前置 → 需补收付款校验、前端表单联动及存量数据处置方案；
- 供应商对账需要启用 → 需重建模块（当前无实现）。
