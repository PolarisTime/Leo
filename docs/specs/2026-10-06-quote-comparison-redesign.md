# 报单比价模块整体设计提案

## 1. 结论

把模块分成「报单需求 → 供应商原始报价 → 比价选价 → 采购跟踪」四个连续环节。以品牌进入报价维护，但报价事实按供应商、完整商品规格和报价时刻分别保存；报单比价保存选价结果，不承担原始报价台账的职责。

首版聚焦快速录报价、逐规格比较、明确选价和历史留痕。保留现有项目配置、网价来源与参照时段、品牌与运费、报单吨位、编辑锁和采购订单明细关联。供应商门户、复杂评分和自动采购不纳入首版。

## 2. 公开产品调研与取舍

| 来源 | 已核对的做法 | 对本项目的借鉴 |
| --- | --- | --- |
| [Odoo 18：Call for tenders](https://www.odoo.com/documentation/18.0/applications/inventory_and_mrp/purchase/manage_deals/calls_for_tenders.html) | 为不同供应商建立关联询价单，在 Compare Product Lines 中按商品行并排比较，再决定向哪家采购哪些商品 | 保留各供应商的原始报价，按规格展示候选，允许不同规格选不同供应商 |
| [Microsoft Dynamics 365：RFQ 概览](https://learn.microsoft.com/en-us/dynamics365/supply-chain/procurement/request-quotations) | 比较行价、交付日期、总价等，可接受部分报价行；询价也可包含运费和折扣 | 价格之外显示数量与交付条件；报单选择和采购执行分开 |
| [Microsoft Dynamics 365：录入和比较投标](https://learn.microsoft.com/en-us/dynamics365/supply-chain/procurement/tasks/enter-compare-rfq-bids-award-contracts) | 比较页并列显示供应商回复、行数量、净额、交期偏差及可选评分 | 候选必须同口径比较；评分可后置，首版先做好价格来源和可执行性 |

上述产品面向完整询价流程。本项目的高频钢材报单以内部快速录入为主，取其「逐供应商留原始报价、逐明细比价、逐明细选价」的结构，不照搬招投标审批流程。

## 3. 当前实现与主要问题

- 比价单已有项目/批次、商品行、品牌列、网价日期与时段、现货价、差价、吨位及采购订单明细关联。现货价表 mk_quote_item_price 对商品行和品牌设唯一约束，因此同一规格、同一品牌在单据中只保留一组现货价和供应商，无法同时查看 A、B 两家候选。
- Aries 当前分别修改现货价和供应商；同商品同品牌的价格联动只复制价格，不复制报价来源。手填后补供应商容易形成无法核实的组合。
- 当前「差价最优」按“参照网价 − 现货价 − 品牌运费”最大值标记。这反映相对网价的空间，不等于跨品牌的最低到场采购成本；两种指标需要分别命名和展示。
- 「锁定参照」只固定日期与时段，网价仍随刷新更新。它是编辑保护，不是历史价格快照；确认后的报单若要复盘，必须额外冻结当时使用的价格与计算依据。
- V168—V172 曾引入供应商价格表，相关功能随后因维护成本和交互复杂度回退；旧表及脚本仍在。新方案不能直接恢复过去的大型可编辑矩阵，也不能修改已执行的迁移。

## 4. 目标业务流程

1. **建报单需求**：选择项目和报单日期，录入商品类别、材质、规格、长度、吨位及品牌限制；选择参考网价数据源、地区、日期和时段。
2. **录供应商报价**：以品牌为入口查看供应商。一次只编辑一家供应商的报价，报价时刻默认当前时间；只录实际报价的完整商品规格。再次调价可复制上一版，预览变动后发布新版本。
3. **逐规格比价**：按需求行展开候选，过滤不符合品牌和规格约束的报价，并核验报价时效与可供数量；数量不足的候选仍可查看，但不作为覆盖整行吨位的默认推荐。分别展示到场价、网价差、供应商、报价时间及报价条件，由人工确认选价。
4. **确认并跟踪采购**：明确保存每行最终选用的品牌、供应商及报价版本，冻结计算依据；继续沿用采购订单明细关联与已开/剩余吨位统计。后续新报价只提示，不静默改写已确认结果。

## 5. 页面设计

### 5.1 品牌报价台账

- 品牌列表作为入口；选中品牌后展示供应商卡片，每张卡片显示最近报价时刻、已报规格数、较上一版变动数及报价状态。
- 点击供应商进入单家编辑器。规格行显示「类别 / 材质 / 直径 / 长度 / 价格」，默认优先展示当前报单涉及的规格，并允许查找其他已有商品规格。
- 「复制上一版」复制该供应商、该品牌的完整报价集合。发布前显示新增、改价和取消报价的差异；空白明确为「未报价」，不使用 0 表达缺报。
- 报价历史按业务报价时间和系统录入时间双时间展示。同日多次调价分别留存，旧版本只读；错误版本通过作废标记处理，不覆盖或物理删除。
- 页面不采用「所有品牌 × 所有供应商 × 全规格」的可编辑大矩阵；如需横向核对，可提供只读比较视图。

### 5.2 报单比价工作台

- 主表以需求规格为行，优先显示吨位、已选方案、到场价、网价差、候选数与采购进度。点开一行后按品牌分组展示各供应商候选，避免大量品牌和供应商同时占据主表宽度。
- 候选行同时显示供应商、报价时刻、价格口径、报价单价、运费、到场价、参照网价、网价差和可供量。缺报、过期、无网价或条件不一致均用文字说明原因。
- 选用候选时，价格、供应商、品牌、报价版本和时间一次写入，不再先手填价格后补供应商。手填保留为例外入口，并标记「手填」及操作人，不伪装为供应商报价。
- 把「到场价最低」和「网价差最大」分成两种明确指标。默认按有效候选的到场价排序，现有差价仍作为分析指标；指定品牌等业务约束优先于价格排序。
- 单据关联采购订单后仍能查看当时的选价依据，不能仅用已采购遮罩隐藏历史比较结果。

## 6. 核心数据与计算规则

### 6.1 报价版本

一份供应商报价版本至少包含供应商 ID、品牌、业务报价时刻、系统录入时刻、录入人、状态和若干报价行。报价行的匹配键为「类别 + 材质 + 规格 + 长度」，价格使用精确十进制，必须大于 0；雪花 ID 对外统一为十进制字符串。

每个版本是该供应商、该品牌当时可报价规格的**完整集合**：没有出现的规格即本版未报价，不从更早版本暗中继承。为减少输入，编辑器可从上一版完整复制后修改。某供应商只报 12、14 时，16、18 不产生候选；同日再次修改 12 时，形成带独立时间的新版本，旧版可查。

业务报价时刻与系统录入时刻分别保存，排序以业务报价时刻为主，同刻用系统录入时刻及 ID 稳定决胜。作废版本不参与新的推荐；旧报单已确认的快照不因此变化。跨日沿用和过期阈值在业务确认前不自动启用。

### 6.2 规格与候选

- 供应商报价必须精确匹配品牌、类别、材质、规格和长度；归一化规则由后端统一维护。现有 HRB400E 兜底和 12 米加价只影响参考网价，不能暗中改写供应商报价的材质或长度。
- 报价有效性、可供数量和价格口径须能解释。未维护可供量时不能声称「库存充足」；数量不足的报价可展示，但不可作为覆盖整行吨位的默认推荐。
- 首版一行最终选一家供应商；若同规格吨位需拆给多家，先拆成多条需求行。未来有稳定需求再引入行级分配，不提前增加配额模型。

### 6.3 可比价格

| 指标 | 计算口径 |
| --- | --- |
| 到场价（元/吨） | 同口径供应商报价单价 + 适用运费 + 明确的其他必要费用 |
| 网价差（元/吨） | 同品牌、同规格的参照网价 − 到场价 |
| 预计采购成本 | 到场价 × 本行拟采购吨位 |

首版明确报价是否含税、是否含运、单位和提货/到货口径；只有口径可比的报价才进入自动排序。当前项目品牌运费可作为默认运费，但不同供应商或仓库存在不同运费时须记录实际口径，已含运价格不得重复加运费。无参照网价时仍可比较到场价，但网价差标记「无参照」。

### 6.4 确认快照与编辑保护

确认每行选价时至少冻结：选用品牌、供应商和名称、报价版本及报价时刻、报价单价、使用的运费、到场价、参考网价的数据源/地区/日期/时段及价格值、兜底与加价标记、网价差、操作人和确认时间。重新选价产生新的决策记录或修订留痕，不能只覆盖旧结果。

现有签出编辑锁、行规格/吨位锁和参照日期/时段锁继续各司其职；它们不等同于业务确认或快照冻结。历史单据不会因报价台账或行情源刷新而自动改变。

## 7. 技术落地边界

- 原始供应商报价使用独立的批次与明细资源；现有 mk_quote_item_price 保持「单据行 × 品牌的一组比较结果」语义，不改其唯一键来容纳原始候选。再新增明确的行级最终选价及来源快照，避免把「候选」「品牌比较结果」「最终采购选择」混成一条记录。
- 先只读核查停用的 mk_supplier_price_list 等旧表在各环境是否有数据，再决定迁移或保留。通过高于当前最高版本的新增 Flyway 脚本实现；不得重写 V168—V172 或既有基线。
- 新接口遵循 /api/v2 的资源命名和契约：创建报价批次返回 201 与 Location，集合查询分页，作废与新版本发布须有权限、审计、幂等与并发保护；错误返回统一 ProblemDetail。现有单据接口仅做兼容性新增，历史手填数据继续按手填来源读取。
- 报价候选查询和推荐规则在后端集中实现，前端只负责展示与明确选用；规格归一、时效、金额精度和供应商权限不能在页面各自复制一套。
- 先并行启用新报价入口，保留现有手填和旧报单。旧报单不批量追溯匹配供应商历史报价，也不自动刷新价格。

## 8. 分阶段实施

| 阶段 | 范围 | 可独立验收的结果 |
| --- | --- | --- |
| 1. 报价台账 | 核对旧数据；新增报价版本、明细、权限与品牌优先录入页 | A、B 对同品牌不同规格报价可分别保存；同日多版可追溯、可作废 |
| 2. 比价接入 | 候选查询、到场价与网价差、逐行选价及来源标记 | 缺报不产生虚假价格；价格与供应商原子选入；历史手填仍可用 |
| 3. 确认与采购 | 结果快照、复盘视图、采购订单明细联动与状态提示 | 行情刷新或供应商调价不改变已确认结果，采购吨位可继续核对 |

## 9. 验收场景

1. 同品牌下 A 报 12/14/16/18，B 只报 12/14：12、14 同时显示两家候选，16、18 仅有 A，B 显示未报价而非 0。
2. A 在 10:00 和 14:30 两次调价：两版保留时间和差异；14:30 前已确认的报单仍显示当时价格，新报单按有效时刻显示新版。
3. 报价单价相同但运费不同、一个报价已含运、某行无网价或可供量不足：比较口径清晰，系统不错误推荐。
4. 同一商品在单据中重复出现：联动后的价格、供应商及来源一致，不出现只复制价格的孤立单元格。
5. 手填旧单、无权限、供应商停用、重复提交、并发调价、报价作废、超大雪花 ID 和小数精度均有明确结果；接口状态码、OpenAPI、前端类型和自动化检查一致。

## 10. 待业务确认

实施前确认以下口径，默认建议已写在上文，确认后才能固化自动推荐规则：

1. 供应商报价跨日是否继续有效，或只在报价当日可自动推荐；若跨日有效，过期提醒阈值是多少。
2. 报价是否统一为含税出厂价、元/吨；是否需要首版就支持供应商/仓库专属运费及已含运报价。
3. 同一规格吨位是否常需拆给多家供应商；若常见，应把拆量模型提前到第二阶段。
4. 采购决策的主排序是「到场价最低」还是「网价差最大」；建议前者为默认推荐、后者为单独展示的分析指标。
