- 报告时间：2026-10-09 11:55 CST
- 故障环境：`/instance/steelx`（leo 生产测试环境，`https://in1love.com`）

- 故障性质：**根文件系统（`/`）写满 → PostgreSQL 崩溃恢复循环 → 数据库不可用**（非应用代码缺陷）

## 一、结论摘要

1. 生产环境在 **10:19:25–11:20:02（约 1 小时）** 期间根文件系统 `/` 被写满。
2. 直接后果：
   - PostgreSQL 18 无法写盘 → **PANIC** → **就地崩溃恢复循环（11:14:17–11:20:04）**，期间所有连接被拒绝（`FATAL: the database system is in recovery mode`）；
   - 生产后端 Hikari 连接池归零（`total=0`），依赖数据库的接口返回 **503/500**，定时任务连续失败；
   - Redis 无法写 RDB（`MISCONF ... stop-writes-on-bgsave-error`）→ 缓存与会话类写命令被拒。
3. **11:20:04 自行恢复**（空间被释放后 PG 完成恢复）；后端从未重启（JVM PID `3675244` 自 11:14 至 11:20 未变）。
4. 当前（11:50 复测）后端、PostgreSQL、Redis、前端全部正常，根盘 `/` 使用率 69%（22.3 G 可用）。
5. **最严重的过程缺陷：故障全程无告警。** `GET /api/v2.0/health` 在整个故障期间始终返回 `{"status":"UP"}`。

   > **订正（14:5x 复核）**：初稿曾判断"该健康检查不探测数据库/Redis"，经核对**已部署制品后确认该判断有误**。`leo-backend-v12.2.0`（`leoSha=40e32a0`，与 tag `v12.2.0` 完全一致）**已包含** DB/Redis 真实探测：`HealthService.health()` 执行 `SELECT 1` 与 Redis `PING`，任一失败即返回 `DEGRADED` 且 `HealthController` 回 503。核验方式：`git show v12.2.0:.../HealthService.java` 与 jar 字节码常量（`DEGRADED`、`SELECT 1`、`health redis check failed: {}`、`ping`）。
   >
   > 因此真实缺口是**没有定期轮询与告警**，以及**基础设施水位/日志特征完全未采集**；且 `HealthResponse` 只含 `status`+`timestamp`（无依赖明细），503 时无法从响应体判断是 DB 还是 Redis 故障。详见第七章 P0-0。

### 为什么监控与 systemd 都"没看到"

- postmaster 进程 **PID `1848284` 全程未变**（`systemctl show postgresql-18`：`NRestarts=0`，`ExecMainStartTimestamp=2026-08-24 14:29:58`）。
- PostgreSQL 遇到后端 PANIC 时会在 **同一 postmaster 进程内 kill 全部子进程并就地重做崩溃恢复**，因此 systemd 显示 `active (running)`，`pg_postmaster_start_time()` 也仍是 08-24（已运行 45 天）。
- 结论：**"systemd active + postmaster 未重启"不能证明数据库可用**，必须依赖 `pg_is_in_recovery()`、连接可用性与真实健康检查。

## 四、根因分析

### 4.1 已确认（证据充分）

**根因 = 根文件系统 `/` 写满。** 三个独立进程同时报 ENOSPC，无法用其他原因解释：

| 进程 | 报错 | 路径所在文件系统 |
| --- | --- | --- |
| systemd-journald | `Failed to create new system journal: No space left on device` | `/var/log/journal` → `/` |
| PostgreSQL 18 | `could not write file ... No space left on device`、`SQLState 53100` | `/var/lib/pgsql` → `/` |
| Redis | `MISCONF ... not able to persist on disk`（RDB bgsave 失败） | `/var/lib/redis` → `/` |

应用侧表现为 `53100`（写盘失败，53 次）先出现，随后才是 `57P03`（恢复期拒连，21 次）——时序与"先写满、后崩溃恢复"完全吻合。

### 4.2 已排除（逐项验证）

| 假设 | 结论 | 证据 |
| --- | --- | --- |
| PostgreSQL `pg_wal` 膨胀占满磁盘 | **排除** | `/var/lib/pgsql` 合计 **558.7 MB**；`pg_wal` **80 MB / 7 个 WAL 段**（`max_wal_size=1024MB`，正常）；`pg_ls_waldir` 7 段 |
| Docker 容器日志无上限（json-file 无 max-size） | **排除为主因**，但**配置缺陷仍存在** | 全部容器 json 日志最大 **15.6 MB**（easybot），napcat 9.2 MB |
| CI（GitHub Actions）任务占用 | **排除** | runner 日志显示 10:19–11:20 期间仅约 50 分钟一次的**空闲心跳**（`RSAFileKeyManager` / `AAD Correlation ID`），无 job 运行、`_work` 无变更 |
| `systemd-tmpfiles-clean` 清理了空间 | **排除** | 定时器在 **14:38** 运行，最后一次为 10-08 14:38 |

### 4.3 未最终定名：约 22 G 空间占用的归属

这是本报告**唯一的未决项**，需明确说明证据边界：

- **当前 `/` 的 47.7 G 已被完整对账**：`/swapfile` 16 G、`/usr` 5.7 G、`/tmp` 6.9 G（其中 `/tmp/opencode` 5.2 G）、`/var` 15.7 G（含 containerd 8.8 G、journal 3.8 G、pgsql 0.56 G、dnf 缓存 0.92 G）、`/opt` 1.9 G、`/root` 0.5 G、`/boot` 0.34 G、`/etc` 0.17 G。**任何地方都不存在 20 G 级文件**。
- 全盘 `≥100 MB` 文件扫描：最大者即 `swapfile`(16 G)，其次 `easybot` 日志包 0.43 G。
- **故障窗口内没有任何 `≥20 MB` 文件被写入**；**11:14–11:23 没有任何目录 mtime 变化**（即没有文件被创建/删除/改名），**11:18–11:21 也没有任何大文件被截断**。
- 结论：这 22 G 属于**元数据静默释放**，即不留下目录/文件元数据痕迹的形态，只有两种可能：
  1. 某进程持有"**已 unlink 但仍打开**"的大临时文件（unlink 发生在更早时刻、早已改动目录 mtime；只有 fd 关闭或进程退出时才归还空间）；
  2. XFS **预分配（speculative preallocation，块在 EOF 之外）或延迟分配**被该写入者终止时一次性回收。
- 与 mlocate 快照（今日 00:00，5,038,710 条路径）的精确差集（8,360 条消失，已在 4.2 逐条归类）**没有发现任何大文件在"曾存在→已消失"之列**，说明该 22 G **不是今日 00:00 之前就存在的普通文件**；结合"文件 mtime / 目录 mtime 双向无痕"，与上述第 1 种形态（今晨创建、随即 unlink、以 fd 持有的临时文件）**最为吻合**。
- 11:20:02 前后可见的宿主事件：`CROND` 在 11:20:01–11:20:02 执行 `tg-sign-cf/reminder_poll.py`（每分钟级任务，非特殊），以及 **11:18:09 有一次来自 `10.10.10.254` 的 SSH 登录（`pts/3`，无 logout 记录）**——即空间释放与一次人工/外部会话在时间上高度吻合；`tg-sign-cf/logrotate.state` 亦在 11:17 被更新（说明当时有 logrotate 相关动作）。
- 需要强调：本机同时运行多个自动化/AI 代理与无头浏览器（见 4.3 上段进程清单），这类进程常以 `O_TMPFILE`/`mkstemp`+`unlink` 方式写大临时文件，且其产物集中在 `/tmp`（位于 70 G 的 `/` 上）。**这是与全部观测特征一致的方向，但现存证据已无法指认具体文件与具体进程。**

**倾向性判断（待确认，非结论）**：本机同时运行多个自动化/AI 代理与无头浏览器（`claude --dangerously-skip-permissions` ×2、`opencode serve --port 4096`、`opencode-telegram`、`dsh` node、`chrome-devtools-mcp` Chrome、Playwright headless Chromium、VS Code Server），其临时产物集中在 `/tmp`（位于 70 G 的 `/` 上，当前仍占 6.9 G，其中 `/tmp/opencode` 5.2 G）。**这类"代理构建/下载/自动化"任务是最符合上述特征（大临时文件、元数据静默释放）的嫌疑来源**，但现存磁盘证据已无法指认具体文件。要闭环需依赖下述手段（见第七章 P1）。

### 4.4 促成这次事故的两项基础缺陷

1. **单点容量设计**：PG 数据、Redis 数据、journal、`/tmp` 全部挤压在 70 G 根盘；875 G 的 `/home` 只放制品与下载（`/instance/aria2/Downloads` 已占 **326 G**，含一个 82 GB 视频文件）。
2. **可观测性缺口**（订正后的准确表述）：
   - **无任何定期轮询**：`/api/v2.0/health` 实现合格（见第一章订正），但没有任何探针/监控系统调用它，因此它是否为 UP 无人知晓；
   - **无磁盘/inode 水位采集**：未安装 sysstat（`/var/log/sa` 不存在），无 netdata 磁盘告警规则；
   - **无日志特征告警**：`SQLState 53100`/`57P03`、`MISCONF`、`No space left on device` 均无规则；
   - **无告警通道**：上述任一信号都没有接收方；
   - **健康响应无依赖明细**：`HealthResponse` 仅 `status`+`timestamp`，503 时无法区分 DB 与 Redis 故障。

## 七、处置建议

### P0（防复发，建议立即执行）

> 已交付物（本仓库）：`scripts/monitor/` —— 生产健康守卫、systemd unit/timer、幂等安装器（支持 `--dry-run`）
> 与 root 运行手册 `runbook-p0-root.md`。落地步骤见该目录 `README.md`，本章 P0-0/P0-1/P0-2 与其一一对应。

1. **P0-0 部署健康守卫并接入告警**（本次"全程无告警"是最大教训；缺口是**轮询与采集**，不是端点实现）

## 十、结论

本次生产故障**不是应用代码缺陷**，而是"**根文件系统写满 → PostgreSQL 就地崩溃恢复 → 数据库不可用**"的基础设施可用性事件。放大因素（订正后）：**没有任何定期轮询去调用本已合格的健康端点、没有任何磁盘/日志水位采集、没有任何告警接收方、也没有留下可归因的文件操作痕迹**，最终表现为"无告警的约 1 小时降级 + 6 分钟中断"。

当前系统已恢复正常，但**根因（根盘容量单点与缺少可观测性）尚未消除**，且**约 22 G 空间占用者的身份因元数据静默释放在磁盘上已不可追溯**。P0 交付物已就绪（`scripts/monitor/` + root 运行手册），建议按 P0-0 → P0-3 顺序落地，并按 P1 处理根盘容量与可归因能力。
